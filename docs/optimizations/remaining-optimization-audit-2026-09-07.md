## 3. 详细建议

### D-01：超时不能只结束 HTTP 等待，扫描预算应覆盖整个导出

**证据**：`argus_py/api/routes/diagnostics.py:79` 的 `_guarded` 在 semaphore 内对 `run_in_thread` 使用 `asyncio.wait_for`；`argus_py/observability/context.py:83` 实际提交至 `run_in_executor`。已经开始的同步线程不会因取消等待而自动停止，超时退出上下文后 semaphore 却已释放。`diagnostics_export.py:170` 的 `_collect_events` 多次调用 `store.search`，而 `diagnostics_store.py:311` 每次重新初始化扫描预算。

**触发与影响**：慢磁盘、较大日志或精确级别筛选命中稀疏时，一次导出会累计消耗多份单页预算；请求超时后新请求可继续进入，旧线程仍在扫描/压缩。普通导出若在超时后才返回路径，不会走到创建 `FileResponse` 的下载清理逻辑。

**建议**：在既有执行边界引入每次操作共享的字节预算、单调时钟 deadline 与协作取消标志，并在读取块/分页/压缩阶段检查。闸门许可应在真实后台工作结束后释放；保留并追踪后台任务，对超时后产生的结果负责清理。不要只增加超时或线程数，也不要全局修改 `run_in_thread` 影响其他用例。

**验收**：用可控阻塞的假 store 模拟多个超时请求，确认实际在途工作不超过配置上限；累计读取字节不超过导出级预算；超时返回后没有未登记 ZIP 遗留。需要覆盖请求取消和关闭容器路径。

**兼容**：可保留现有 429/503 与 `scanLimited` 字段；限制收紧可能使过去长时间扫描的请求更早截断，应记录原因与实际扫描量。

### D-02：跨组件采集与跨文件排序需要统一语义

**证据**：`diagnostics_export.py:202` 按 components 输入顺序采集，第一组件可用完全部 `max_events`，最后才对已采集结果排序。`diagnostics_store.py:491` 的候选文件按 mtime 排序，`search` 逐文件收集达到 limit 即停止，没有按事件时间跨文件归并。

**最小反例**：指定 `[python, java]`，`maxEvents=1`，Python 有一条 10:00 日志，Java 有一条 11:00 日志。当前采集可在 Python 阶段填满，完全不读取 Java，最后排序无法补回 11:00 的事件。即使不传 components，也不能把文件 mtime 顺序当作事件时间顺序。

**建议**：先明确“最新 N 条”是否为公开语义；若保持现有注释的新→旧语义，在 store 层提供有界多源归并与稳定复合游标，export 复用，不各自维护另一套排序分页。归并必须考虑文件内时间回退、轮转、同时间戳及扫描预算耗尽；无法保证完整最新集合时明确标记，不以最终一次 sort 掩盖漏读。

**验收**：互换 components 顺序结果一致；构造文件 mtime 与事件时间相反、跨页同时间戳和轮转数据，验证无重复、无静默漏项，并验证预算不足时的标记。

**兼容**：排序改变会影响分页游标；如调整游标格式，应版本化并定义旧游标的兼容或显式失效行为，不静默跳过日志。

### D-03：TTL 不等于容量上限，下载需要独立占用状态

**证据**：`diagnostics_export.py:71` 的 `DiagnosticsBundleRegistry` 只有 TTL，没有条目数/总字节上限；仅 `put/get` 触发过期回收。`get` 持锁执行 `_purge_locked`，后者同步 unlink；`api/routes/diagnostics.py` 的 `download_diagnostics_bundle` 在异步路由直接调用 `registry.get`，响应结束才 pop 并删文件。

**触发与影响**：15 分钟内持续创建而不下载可累计大量包；停止访问后过期文件不会仅因 TTL 到达而及时清理。两个下载可取得同一记录，其中一个完成后删除文件可能影响另一个尚未打开文件的响应；Windows 文件占用还可能使清理失败。过期批量删除也会在下载路由占用事件循环。

**建议**：增加包数量与总字节准入，复用组合根生命周期定时清理；锁内只变更元数据，磁盘 IO 在线程边界执行。下载采用原子领取或引用计数，清理器跳过在用包，并对删除失败保留可重试记录。保持重启后包 ID 失效的现有契约。

**验收**：创建至容量上限、空闲过期回收、并发下载、下载期间到期以及 Windows 删除失败；断言文件仍受追踪、下载行为确定、事件循环无同步批量删除。

**兼容**：容量拒绝及重复下载处理中状态需要稳定响应语义；如新增配置/API 字段，同步 schema、前端生成类型与契约测试。无需数据库迁移。

### D-04：ZIP 异常清理与 manifest 的真实性

**证据**：`build_log_export` 和 `build_diagnostics_bundle` 使用 `NamedTemporaryFile(delete=False)`，`finally` 仅 close，序列化/写 ZIP 失败时没有删除未完成文件。诊断包 `_write_json` 预算不足即跳过写入，但 `contents` 按请求选项生成；系统事件读取异常也只打 debug。最后写 `manifest.json` 同样受剩余预算控制，因此剩余空间不足时 manifest 本身可被跳过。

**建议**：由构建函数管理未交付文件的异常清理，交付成功后再转移所有权。预留 manifest 预算并保证始终存在；按实际写入条目构建 `contents`，记录 omitted 文件及原因。系统事件读取失败应反映为包内可观察的降级信息。

**验收**：注入序列化异常、写盘异常、系统事件查询异常和接近字节上限的输入；断言失败无未登记残留，成功 ZIP 必有 manifest，`contents` 与实际成员一致。

**兼容**：manifest 新增降级字段采用兼容新增；不改变现有 ZIP 成员名。清理失败需记录并重试，不能覆盖原始异常。

### D-05：先消除可见的重复物化，再测量性能收益

**证据**：`diagnostics_store.py:584` 的 `_read_reverse_lines` 一次读取最多整个字节预算，`splitlines` 后构建并解码全部记录；调用者通常只需要 100～200 条。`diagnostics_export.py:307`、`:423` 又分别保留事件列表、JSON 行列表和 join/encode 后的 NDJSON，最后 `writestr`。现有约 50 MiB 限制针对序列化内容，不是进程峰值内存上限，也不是精确 ZIP 文件尺寸上限。

**建议**：store 使用有界反向块迭代，足够产生本页及续页探测记录时停止；ZIP 通过成员写句柄逐行编码写入，共享序列化写入工具。与 D-01 的累计预算和 D-02 的归并游标一起设计，避免只改写入端却保留上游大列表。

**验收**：对固定大日志集记录读取字节、查询耗时和峰值内存，对比分页 100/200 条及导出 5000 条；增加超长单行、UTF-8 跨块边界与轮转场景。性能提升幅度待测量，不预先承诺百分比。

**兼容**：保留 NDJSON UTF-8 编码、脱敏、ZIP 成员名与查询字段；无需新依赖或数据库变更。

### D-06：区分“达到上限”和“确实存在未导出的匹配项”

**证据**：`diagnostics_export.py:232` 在 remaining 归零时使用 `page.has_more or bool(page.items)` 设置 truncated；此时 page.items 必然非空，因此恰好 N 条匹配日志、上限也为 N 时同样返回 true。

**建议**：多探测一条符合完整过滤条件的事件，才确认条数截断；预算耗尽保留 `scanLimited`，不要将未知是否有更多与已确认条数截断混同。精确 levels 过滤时，store 的 has_more 只表示候选项仍有更多，不能直接代表还有符合最终过滤的事件。

**验收**：覆盖 0、N-1、N、N+1 条，及后续候选全被 levels 过滤、扫描受限场景；响应头、回执与 manifest 标记一致。

**兼容**：字段不变，修正错误的 true 值；前端可沿用现有展示。
